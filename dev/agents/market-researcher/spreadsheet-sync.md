# Does the spreadsheet sync (Task 752) rest on outside evidence? (2026-10-17)

Method: web search plus a few page fetches. Bentley's community site now redirects to a login-style portal (bentleysystems.service-now.com), so forum threads were readable only as search summaries. No numbers on how many users do any of this exist; I looked and found none.

## VERDICT (plain words, for Tom)
Narrow it. The outside evidence says people really do move data between spreadsheets and their model, but mostly ONE-WAY and mostly about ELEMENT data (demands from meter or billing sheets, pump curves, patterns, pipe attributes), not whole scenario trees. Bentley's own tool, the one you admired, is built around exactly that: a saved connection to an Excel file, run in (Sync In) or out (Sync Out), working on the CURRENT scenario. I found NO evidence anyone wants a live Google Sheets link, and some reason to doubt it. So: keep the file version (ODS, with CSV as the simplest door), make it work on one scenario at a time with a clear "which scenario/alternative does this go into" question (that is Task 814's job and it fits), and do NOT build the Google Sheets link until a real user asks for it. The round-trip of the whole project is a want of yours, not one I could find in anyone else's practice.

## A. What I found (cited)

Q1/Q2. Do modellers do this, and what does the commercial tool offer?
1. Bentley ModelBuilder is the established tool. A "connection" holds the rules from a source (Excel, Access, shapefile, geodatabase) to the model, is saved in an external XML file not in the model, and has Sync In (source to model, whole model or a selection set) and Sync Out (model to source; updates only elements that exist in both). https://prd-aws-docs.bentley.com/LiveContent/web/Bentley%20WaterGEMS%20SS6-v1/en/40009.html ; Excel-specific: https://docs.bentley.com/LiveContent/web/Bentley WaterCAD CONNECT Edition Help-v1/en/GUID-E7017889-7119-4A6E-98A6-CCA54E6E0607.html (lists Excel, Access, dBase, shapefiles, Oracle, SQL Server as sources; page does not mention scenarios).
2. Scenario handling in ModelBuilder is "the current one": WaterCAD help says Sync Out refreshes the source with current model values for the current scenario/alternative; a forum answer says a ModelBuilder tab specifies which scenario the import updates, and warns that importing into a child scenario can leave elements inactive in other scenarios; the advice is to import NEW elements into Base. (Search summary of https://communities.bentley.com/products/hydraulics___hydrology/f/haestad-hydraulics-and-hydrology-forum/238916/pipes-updated-in-model-builder-coming-into-model-as-inactive ; I could not open the thread.)
3. Demand import from a spreadsheet is a documented, common task. Bentley's TechNote "Importing Demands From A Spreadsheet" (https://communities.bentley.com/products/hydraulics___hydrology/w/hydraulics_and_hydrology__wiki/3100/importing-demands-from-a-spreadsheet) per search summary: matched on a label column; import REPLACES existing demands on listed nodes and cannot update one demand where a node has several. A forum thread (https://communities.bentley.com/products/hydraulics___hydrology/f/haestad-hydraulics-and-hydrology-forum/92788/importing-demands-into-an-existing-model-from-excel-data/267770) has a poster with about 13,000 customers and monthly meter reads in Excel asking how to get them into an existing model. I saw only the question. This is the clearest real-user case: one-way, billing/meter to demands.
4. Round-trip exists but is aimed at keeping a source file current: Bentley TechNote "Updating Source File using ModelBuilder" says keeping the source and model synchronized "is often a challenge" and recommends Sync Out. https://communities.bentley.com/Products/Hydraulics___Hydrology/w/Hydraulics_and_Hydrology_Wiki/updating-source-file-using-model-builder.aspx (summary only). Known defect reports: start/stop nodes not exported on Sync Out to a geodatabase (workaround: sync out to Excel) https://communities.bentley.com/products/hydraulics___hydrology/f/haestad-hydraulics-and-hydrology-forum/190939/start-and-stop-nodes-are-not-exported-in-sync-out-using-arcgis-geodatabase-features-with-modelbuilder-1/566394 ; a request to automate Sync In from ModelBuilder in ArcGIS https://communities.bentley.com/products/hydraulics___hydrology/f/haestad-hydraulics-and-hydrology-forum/178300/automate-the-sync-in-from-modelbuilder-in-arcgis/518305 (older, V8i era). Bentley recommends Access over Excel because Excel will not let you fix column data types (https://communities.bentley.com/products/hydraulics___hydrology/w/hydraulics_and_hydrology__wiki/2645/importing-time-series-data-using-modelbuilder-tn).
5. Bentley has NO documented Excel round-trip of scenario/alternative structure. Its only scenario exporter is an unofficial, untested tool that produces a report, not an editable file: https://communities.bentley.com/products/hydraulics___hydrology/w/hydraulics_and_hydrology__wiki/41167/generating-a-report-of-scenarios-and-alternatives-in-a-model . The Scenario Comparison tool compares inputs only; no results comparison as of 10.03.02 (Enhancement 60965): https://communities.bentley.com/products/hydraulics___hydrology/w/hydraulics_and_hydrology__wiki/19839/scenario-comparison . Results to Excel needs a FlexTable per element type: https://communities.bentley.com/products/hydraulics___hydrology/w/hydraulics_and_hydrology__wiki/29064/export-time-series-data-to-excel-or-csv-format
6. InfoWater Pro: a vote-6 "gathering support" request (2026-05-07) for built-in fire-flow comparison across scenarios; today the user "exports both and compares manually". https://innovyzefeedback.autodesk.com/ideas/INWAPRO-I-262 . Demand allocation uses meter layers, including a tool to make a meter layer from a spreadsheet (search summary; not fetched). That is a complaint about COMPARING RESULTS, not about moving scenario inputs.
7. EPANET itself: the manual says scenario files (demands, diameters, roughness, controls) are plain ASCII, editable "using a text editor or spreadsheet program"; EPANET has no scenarios, and Bentley states only data both formats support survives an .inp pass. https://epanet-manual.readthedocs.io/en/latest/11_importing_exporting.html ; https://communities.bentley.com/products/hydraulics___hydrology/w/hydraulics_and_hydrology__wiki/10274/what-are-the-limitations-of-importing-exporting-epanet-files
8. Researchers and some practitioners script this instead (EPyT, WNTR, EPANET-MATLAB). https://epanet-python-toolkit-epyt.readthedocs.io/en/latest/api.html . Inference: people with scripting skill bypass spreadsheets.

## C. What I think (inference, re-derive before relying)
- Q3: The demonstrated want is one-way IN: meter/billing/GIS tables to demands and attributes. Export-out is mainly for reports and for keeping a source current. A whole-project, whole-scenario-tree round trip has no precedent I can find; Bentley offers none. It would be a differentiator or a solution to a problem nobody has voiced. (Tom's own consulting use is a legitimate source of demand; it is just not outside evidence.)
- For Task 814: the commercial model is "class 1, current scenario": sync works on the active scenario/alternative and asks which one. Bentley's trap (child-scenario import leaves elements inactive elsewhere) is the risk 814's "where does it go" question exists to prevent. Note that ModelBuilder REPLACES a node's demands wholesale; an import report that says so before applying is more careful than Bentley.
- Q4: A file is enough. ODS/CSV avoids a fifth third-party service and a privacy.php paragraph. Excel (not Google Sheets) is the working spreadsheet of the evidence; ODS opens in Excel, so ODS is fine. Bentley itself warns Excel's weak column typing causes trouble; a documented, typed template is a plausible advantage.
- Q5, what may matter more to the same users: (a) comparing RESULTS across scenarios (InfoWater vote-6 request; Bentley has no results comparison); we have a scenario tree, so a results-by-scenario table that copies to a spreadsheet is the same plumbing with a documented gap on both big vendors. (b) Demand import from a meter/billing table with an honest "this replaces N demands" report. Both are narrower than a general sync and each has a citation. Weak evidence each; a sample of three, not a market.

## D. Disconfirmation scorecard
Wants round-trip of scenario trees: not supported. Wants element-data in/out via spreadsheet: supported (Bentley built a whole subsystem and TechNotes for it; users ask). Wants live Google Sheets: unsupported. Wants a re-runnable saved mapping: supported by Bentley's design, no user praise or complaint about the Connection concept itself found.
