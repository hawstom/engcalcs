Why the reader cannot reveal them:
- css/engcalcs.css:5629 `--lpn-set-name: 11.5rem` is a CEILING on the name column (Tom's own 2026-08-20 call, made so controls stop floating right). Dragging the box wider gives the extra width to nobody. So the 13 are cut at ANY width. The box IS resizable (`resize: both`, and there is a draggable divider beside the index), but resizing cannot help these 13 because the column will not grow. That is the finding: "guaranteed resizing" does not exist today.
- :5652 `.lpn-set-row > :first-child, .lpn-set-name { overflow: hidden; white-space: nowrap }` clips; :5639 gives the name `minmax(0, ...)`, no floor (Tom, 2026-10-30), so a narrow box squeezes it to nothing. At 240 px the Units row "Head loss gradient" is 0 px wide.
- Neither Settings row carries a tip: the Labels-list "Head loss gradient" is `<label class=lpn-set-name><input checkbox> <span>Head loss gradient</span></label>` with no title. Nothing scrolls; the content pane is `overflow:auto` but the clip is inside it, so there is nothing to scroll.
- "Head loss gradient" appears twice: the Labels list (link fields), which has room down to ~240 px, and the Units list (`lpn-units-item lpn-set-row`), which needs 113 px and gets 104 at a 480 box, 54 at 380, 14 at 300. The Units one is the one Tom met (it is the narrow-box case, and his 2026-10-24 report was a 360 px dock).
- Phone: a box fills the screen, there is no resize corner on touch, the divider is a 6 px strip, and the index takes 71 px, so the name column is 59 px (79 labels cut). No hover. So there is no reveal at all.

Other boxes (OBSERVED in CSS only, widths NOT measured by me): Properties and the Tables-style grids use `.lpn-gname` (css:3895), the same `overflow:hidden; white-space:nowrap`. Their longest names are 33 characters ("Minor (local) loss coefficient, k"). The Labels grid columns wrap (css:6141, `overflow-wrap:anywhere`) but its `label` also wears `.lpn-set-name`, whose `nowrap` wins in Settings, so it clips too. ## 2. The mitigations, judged (phone has no hover; PC has a mouse)

- Ellipsis: Tom ruled it out. It still marks "something is missing", which clipping does not; but it cannot reveal.
- Tip (title on hover): PC yes, phone no (NN/g tooltip guidelines, CITED earlier: tooltips unavailable on touch). Also contradicts Tom's "no tips on cut cells" and "nothing hover-only". Fails the phone, which is the case that matters.
- Tap-to-reveal tip (the ? popup): works on touch, but it adds a glyph to 129 rows, and Tom wants exactly one ? per label, always the manual entry. Wrong job for it.
- Guaranteed resizing: not true today (ceiling, above). Making it true means lifting the ceiling, which re-creates the floating-right paradox Tom fixed in August. On a phone the box cannot grow, so it never helps there. EPANET 2.2's Property Editor does it (columns can be re-sized, manual section 4.8, CITED earlier), but it is a desktop-only fix. WaterGEMS Properties/FlexTables: resizable columns (recall, not refetched, SPECULATION).
- Wrapping: works on phone and PC, needs no gesture, no words, no hover, nothing to learn, and it is already Tom's standing call for label rows ("two lines max, text wrap even mid-word is fine"). VS Code's Settings editor wraps its setting names and descriptions; QGIS forms and the Windows common dialogs wrap labels; I am recalling these, not citing a fetched page (SPECULATION). Cost: a row can grow taller.
- Double-click-to-autofit and horizontal scroll (Excel): autofit is a mouse gesture, unknown on touch. Horizontal scroll inside a box: Tom already said a sideways scroller in Settings is wrong (css:6200 note, 2026-08-19).
- Master/detail strip (WaterGEMS and Visual Studio Properties show the selected property's name and description in a pane at the bottom): reveals on tap and click, but it is a whole new pane and a lot of words.

## 3. Recommendation: wrap the name to at most two lines, with a floor

One change, in the Settings row rule, css/engcalcs.css:5652:
- name cell: `white-space: normal; overflow-wrap: anywhere; overflow: hidden; max-height: 2 lines` (about 2.6em; clip, no ellipsis, as Tom decided);
- name column: floor of about 7rem (`minmax(7rem, var(--lpn-set-name))` instead of `minmax(0, ...)`); the value column keeps its 6rem floor. If the box is narrower than the two floors together, the content pane scrolls sideways as the last resort, which is a way to reveal; the clip never is.
- Keep `--lpn-set-name: 11.5rem` as it is. It stays the column's width, so the August paradox stays fixed; the long names go to two lines of 184 px instead of one cut line.
- The label's checkbox (Labels list) stays on the first line, as Tom's "label and tick, then the input group wraps whole beneath" call says.

What it buys, measured by arithmetic from the table: all 13 cut labels at the default box width fit in two lines (the widest, 322 px, is 1.75 lines at 184). At a 390 px phone box, name column goes from 59 px to 112 px: "Head loss gradient" (113) becomes 2 short lines instead of a stub, and most others fit in two lines; a few of the longest in German or Spanish may still lose a tail, which is why the harness should keep reporting them.

What it costs: rows that wrap are taller (about one extra line, ~14 px; 13 rows at PC default is roughly 180 px more Settings scrolling out of ~4000); on a phone more rows wrap, so Settings is longer; baseline alignment keeps the control beside the first line, which is how it already behaves for the Labels rows. It reverses Tom's 2026-10-30 round 9 call ("no lower limit and truncate instead of wrapping"), so he should be told that plainly. It does not touch Properties, the Tables grid, or Find, where I measured nothing; do those through the harness before touching them (the same `.lpn-gname` rule would take the same change).

If Tom does not want rows to grow: the second choice is the floor alone (no wrap). It makes the phone stub 112 px instead of 59, but 13 labels stay cut on PC at every width, so it is not a mitigation for the case he named.

## Teach-as-you-go terms
- Ceiling vs floor: a ceiling stops a column growing; a floor stops it shrinking. Settings had a ceiling and a floor of zero.
- Clip vs ellipsis vs wrap vs scroll: four ways to deal with too-long text; only wrap and scroll show the reader all of it.
- Reveal: any way a reader reaches hidden text with no special knowledge. A drag handle is a reveal only if the box can actually grow into the text.
