# 2.0. Working together (negotiable)

## 2.1. Roles

### 2.1.1. Major AI responsibilities

This is a PHP/JS hydraulic engineering calculator suite (12 calculators, 27 languages). PHP delivers multi-lingual page rendering; all computation is client-side JavaScript. No database, no authentication. Major AI work falls into four domains:

**Calculator development** — design, UX review, and code editing:
1. Researching, envisioning, recommending, and creating calculators for the developing world
2. Reviewing calculators for UX improvements
3. Editing calculators

**Internationalization** — keeping 27 language files current:
4. Researching and recommending languages for addition or retirement
5. Adding languages
6. Translating new calculators
7. Translating changes
8. Reviewing and auditing translations

**Project maintenance** — roadmap and infrastructure:
9. Maintaining the roadmap
10. Advising and scripting for production server attack management

**Translation tooling and release mechanics** — scripting, file wiring, git:
11. Maintaining translation tooling and payload generation (`scripts/generate_translation_payloads.php` and `translation_payloads/`).
12. Creating and wiring new language files and menu entries (`lib/lang.ec.*.php`, `lib/Menus.lib.php`).
13. Ensuring page includes follow repo conventions (use `filemtime()` for JS includes) when adding calculators.
14. Preparing per-language git branches and commits (e.g., `i18n/xx`) and clear commit messages.
15. Running basic QA on generated language files (syntax, unbalanced quotes, HTML tag preservation) before review.
16. Executing git commits and pushes to production or staging branches.

Copilot's highest-value activities are inline code editing, scripting, and git mechanics. Routing each task to its natural fit avoids paying Claude Code's context cost for mechanical edits and avoids Copilot's weaker multilingual judgment on translations.

## 2.2. Handoff procedures

### 2.2.1. Artifacts and locations
- `lib/lang.ec.en.php` — canonical English source strings. When Claude Code adds keys here, that is the trigger for Copilot's tooling work (IDs 11–15).
- `translation_payloads/` — per-language JSON payloads generated by Copilot scripts; consumed by Claude Code translation agents.
- `scripts/generate_translation_payloads.php` — payload generator maintained by Copilot.
- `ROADMAP.md` — task queue; the shared coordination surface for "Proceed" sessions.
- `translation_reviews/` — short human review notes and flagged terms.

### 2.2.2. Task labeling convention

Tasks in `ROADMAP.md` that require work from a specific actor should carry an actor tag at the end of the description line:

| Tag | Meaning |
|-----|---------|
| `[CC]` | Claude Code owns this task |
| `[CP]` | Copilot owns this task |
| `[H]` | Human decision required |
| `[CC→CP]` | Claude Code acts first, then hands off to Copilot |
| `[CP→CC]` | Copilot acts first (e.g., scaffolds files), then Claude Code translates |

Untagged tasks are actor-agnostic — either platform may pick them up.

**Blocking marker convention:** if Human input is needed before the current owner can continue, prepend `[H]` at the beginning of the task line while keeping the ownership tag at the end. Example: `[H] Clarify unit-set policy ... [CP]`. This preserves ownership while signaling Human-first action.

**Clearing `[H]`:** once Human input is provided and the owner confirms the blocker is resolved, remove the leading `[H]` and continue with the existing ownership tag.

**`[H]`-only tasks (no trailing ownership tag):** these are pure decision tasks — the Human has not yet decided whether to do them or who owns them. When the Human decides "yes," they replace `[H]` with the appropriate actor tag. When the decision is "no," the task moves to Completed with a one-line rationale. `[H]` alone is never a permanent state.

**Tag lifecycle ("hot potato" rule):** Tags show who currently holds the task, not the full history. When the current holder finishes its portion, it updates the tag to the next actor's plain tag:

| Original tag | After first actor finishes | Meaning |
|---|---|---|
| `[CC→CP]` | → `[CP]` | CC's work done; CP now has the ball |
| `[CP→CC]` | → `[CC]` | CP's work done; CC now has the ball |
| `[CC]` or `[CP]` | → `0` in the Priority field (move to Completed) | Task fully done |

Example: CC adds a new calculator's English keys and labels the scaffolding task `[CP→CC]`. Copilot creates the lang file stubs and menu entry, then changes the tag to `[CC]`. Claude Code then runs the translation sprint.

### 2.2.3. "Proceed" session rhythm

The Human sets a **priority floor** (e.g., "Proceed down to priority 90") and activates one platform at a time. The floor is a hard cutoff — tasks below it are invisible until the Human lowers the floor in a later round.

**Within a single session (one platform active):**
1. Platform picks the highest-priority task at or above the floor that is tagged for it (or untagged).
2. Works the task to completion or to its handoff boundary.
3. Leaves a **handoff note** — a brief comment in `ROADMAP.md` or a commit message — stating what was done and what the next actor needs. Example: `[handoff→CP: lang files ready, run payload generator]`.
4. Repeats until no tasks at or above the floor remain for it. Then stops and tells the Human.

**Required handoff note fields (minimum):**
- `Done:` what changed
- `Ready:` what artifact/step is ready now
- `Next:` first action for next actor
- `Blocker:` `none` or concise blocker
- `Files:` key files touched (or `none`)

**Split tasks (`[CC→CP]` or `[CP→CC]`) within a band:** The first actor completes its half and updates the tag to the plain next-actor tag (e.g., `[CC→CP]` → `[CP]`). The second actor picks it up in the same band's session — not a later round.

**Session switching rule:** only the Human switches active platforms. A second actor picking up the split half in the same band means the Human ends actor A's session and starts actor B's session at the same priority floor.

**Actor does not start the other actor's portion.** If CC notices a file-wiring step is needed, it records it and stops.

**Unfinished plain-tag task rule:** if `[CC]` or `[CP]` work is partially done but not complete, keep the same tag, add a handoff note, and add leading `[H]` only if Human input is required.

**Untagged task claiming:** whether the active platform retags an untagged task to `[CC]`/`[CP]` while working is an internal management choice. It is optional and does not affect cross-platform coordination under the one-platform-active model.

**Mid-session reprioritization:** active platform may propose roadmap changes, but priority and scope changes are applied only with Human confirmation.

**Round complete when both platforms say "all done."** The Human then lowers the floor, adds or reprioritizes tasks, and begins the next round.

### 2.2.4. Best practices
- **One platform active at a time.** The Human does not run CC and CP concurrently on this project. The Human is the relay and the lock.
- Agents do not communicate directly — all handoffs go through the Human and the artifact system.
- Keep handoff notes short and actionable: what was done, what is ready, what the next actor should do first.
- When a platform finishes its portion of a split task, update the task description in `ROADMAP.md` to reflect the remaining half (change priority or description) so the next session picks it up cleanly.
- **No side-channel concurrency.** While one platform is active, the other is not run on this project, including read-only review passes. Any review waits for explicit Human handoff.
- **Commit message handoff suffix (recommended):** `[handoff→<CC|CP|H>: <next first action>]`.
